이 과정은 **새 프로젝트의 코드 범위를 정하고 → 프로젝트 설명을 작성하고 → 현재 코드 버전을 검토 완료로 등록한 뒤 → BM25 검색을 확인하는 초기 설정**입니다.

예를 들어 Spring Boot 프로젝트에 적용한다면 다음과 같이 진행합니다.

### 1. 검색·변경 감지 대상 설정

[config.json](C:/workspace/daemon_bms_develop_masked/e-commerce-daemon/install/portable/README.md)을 프로젝트에 맞게 수정합니다.

```json
{
  "source_mode": "portable",
  "guidance_marker": "project-harness",

  "source_globs": [
    "*.java",
    "*.kt",
    "*.gradle",
    "*.xml",
    "*.sql",
    "*.properties",
    "*.yml",
    "*.yaml",
    "*.md"
  ],

  "exclude_dirs": [
    "logs",
    "tmp",
    "generated-sources",
    "frontend-build"
  ],

  "max_source_bytes": 8388608,

  "sensitive_source_globs": [
    "**/application*.yml",
    "**/application*.yaml",
    "**/*DataSourceConfig*",
    "**/*SecurityConfig*",
    "**/.env*"
  ],

  "document_globs": [
    "install/knowledge/**/*.md"
  ],

  "validated_test_classes": [],

  "commands": {
    "build": [
      "gradlew.bat",
      "--no-daemon",
      "compileJava"
    ],
    "test": [
      "gradlew.bat",
      "--no-daemon",
      "test"
    ]
  },

  "review_targets": [
    "install/knowledge/project.md",
    "install/knowledge/testing.md",
    "install/knowledge/database.md",
    "install/knowledge/decisions.md"
  ]
}
```

각 설정의 의미는 다음과 같습니다.

- `source_globs`: 변경 감지와 원문 검색 대상으로 삼을 파일 형식
- `exclude_dirs`: 탐색하지 않을 폴더의 **폴더 이름**
- `sensitive_source_globs`: 해시 변경은 감지하지만 내용은 Hermes 검토 자료나 검색 결과에 직접 싣지 않을 파일
- `document_globs`: BM25로 검색할 Markdown 문서
- `commands`: 해당 프로젝트에서 실제 사용할 빌드·테스트 명령

Node/TypeScript 프로젝트라면 다음처럼 줄일 수 있습니다.

```json
{
  "source_globs": [
    "*.ts",
    "*.tsx",
    "*.js",
    "*.jsx",
    "*.json",
    "*.sql",
    "*.yml",
    "*.yaml",
    "*.md"
  ],

  "exclude_dirs": [
    "storybook-static",
    "playwright-report"
  ],

  "sensitive_source_globs": [
    "**/.env*",
    "**/*secret*",
    "**/*credential*",
    "**/config/production*"
  ],

  "commands": {
    "build": ["npm.cmd", "run", "build"],
    "test": ["npm.cmd", "test", "--", "--run"]
  }
}
```

`node_modules`, `.git`, `.venv`, `dist`, `build`, `target`, `.runtime` 등은 기본적으로 제외됩니다.

### 2. 프로젝트 지식 문서 작성

설치 직후 다음 파일은 빈 프로젝트용 템플릿입니다.

#### `install/knowledge/project.md`

프로젝트 목적, 실행 지점과 주요 경로를 적습니다.

```markdown
# 프로젝트 설명

## 목적

고객 주문을 수신하고 배송사에 전달하는 Spring Boot 배치 서비스다.

## 주요 진입점

- 애플리케이션: `src/main/java/com/example/BatchApplication.java`
- 주문 수신 스케줄: `src/main/java/com/example/order/OrderSchedule.java`
- 주문 처리 서비스: `src/main/java/com/example/order/OrderService.java`
- 주문 SQL: `src/main/resources/mapper/OrderMapper.xml`

## 주요 처리 흐름

1. OrderSchedule이 미처리 주문을 조회한다.
2. OrderService가 주문을 검증한다.
3. 배송사 API를 호출한다.
4. 처리 상태와 응답을 저장한다.

실제 DB 조건과 외부 API 성공 여부는 코드와 실행 결과를 다시 확인한다.
```

#### `install/knowledge/testing.md`

실제로 신뢰할 테스트와 실행 방법을 적습니다.

```markdown
# 테스트 지식

## 기본 명령

- 빌드: `.\gradlew.bat compileJava`
- 단위 테스트: `.\gradlew.bat test`
- 하네스 실행: `.\install\run.ps1 run-check test --execute`

## 검증 기준

- 주문 상태가 READY인 행만 처리한다.
- 같은 주문을 두 번 발송하지 않는다.
- 외부 API 실패 시 주문을 SUCCESS로 바꾸지 않는다.

## 현재 검증 범위

OrderServiceTest는 주문 상태 분기를 검증한다.
실제 배송사 API와 운영 DB 연동은 포함하지 않는다.
```

#### `install/knowledge/database.md`

DB 종류, 주요 테이블과 검증 방법을 적습니다. 비밀번호나 접속 문자열은 기록하지 않습니다.

```markdown
# 데이터 저장소

## DB

- 종류: SQL Server
- 주문 테이블: `dbo.TB_ORDER`
- 전송 이력: `dbo.TB_ORDER_SEND_HISTORY`

## 처리 기준

- `STATUS = 'READY'`인 주문이 처리 대상이다.
- 성공 시 `STATUS = 'DONE'`과 처리 시각을 저장한다.
- 실패 시 원본 주문 상태와 오류 이력을 함께 확인한다.

실제 열, PK, FK, identity와 기본값은 테스트 SQL 작성 전에 현재 DB에서 확인한다.
접속 주소·계정·비밀번호는 이 문서에 기록하지 않는다.
```

#### `install/knowledge/decisions.md`

하네스와 프로젝트에서 유지할 설계 결정을 기록합니다.

```markdown
# 구성 결정

- 소스 변경 시 지식 문서를 자동 승인하지 않는다.
- BM25 결과는 읽을 문서의 후보로 사용한다.
- 외부 API 성공은 실제 HTTP 응답과 DB 결과로 검증한다.
- 테스트 결과와 로그는 `install/.runtime/runs`에 보존한다.
- 비밀값과 운영 업무 데이터는 검색 색인에 넣지 않는다.
```

### 3. 현재 원문 검토 및 기준 등록

먼저 현재 소스를 읽어 자동 생성 문서와 변경 목록을 만듭니다.

```powershell
.\install\run.ps1 sync
```

처음 실행하면 보통 `REVIEW_REQUIRED`가 나옵니다. 설치 실패가 아닙니다.

다음 파일을 확인합니다.

```powershell
Get-Content .\install\knowledge\generated\project-facts.md
Get-Content .\install\knowledge\generated\test-facts.md
Get-Content .\install\knowledge\generated\review-queue.md
```

`review-queue.md`가 예를 들어 이렇게 나온다고 가정하겠습니다.

```markdown
상태: REVIEW_REQUIRED

- added: `src/main/java/com/example/order/OrderService.java`
- added: `src/main/resources/mapper/OrderMapper.xml`

검토 대상:
- `install/knowledge/project.md`
- `install/knowledge/testing.md`
- `install/knowledge/database.md`
- `install/knowledge/decisions.md`
```

이때 해야 할 일은 다음과 같습니다.

1. `OrderService.java`와 `OrderMapper.xml`을 실제로 읽습니다.
2. 앞의 네 지식 문서 설명이 코드와 일치하는지 확인합니다.
3. 누락되거나 틀린 설명을 수정합니다.
4. 검토 내용을 구체적으로 남기며 승인합니다.

```powershell
.\install\run.ps1 accept-review `
  --note "OrderService 처리 조건, OrderMapper SQL, 테스트 명령과 주요 테이블 설명을 현재 원문과 대조함"
```

그다음 문서와 색인을 다시 생성합니다.

```powershell
.\install\run.ps1 sync
```

정상적으로 완료되면 다음과 비슷하게 나옵니다.

```json
{
  "status": "CURRENT",
  "index": "UPDATED",
  "generated_knowledge": "UPDATED"
}
```

`accept-review`는 테스트 통과나 업무 정상 작동을 의미하지 않습니다. **현재 원문과 프로젝트 지식 문서를 사람이 대조했다는 기준점**을 저장합니다.

### 4. 실제 BM25 검색 확인

프로젝트에서 자주 사용할 표현으로 검색합니다.

```powershell
.\install\run.ps1 search-docs "주문 전송 실패" --limit 3
```

예상 결과는 다음 형태입니다.

```json
{
  "status": "FOUND",
  "engine": "JSON BM25; no semantic search or answer generation",
  "results": [
    {
      "path": "install/knowledge/project.md",
      "start_line": 1,
      "excerpt": "...",
      "sha256": "...",
      "score": 4.27
    }
  ]
}
```

검색 경로 전체도 검사할 수 있습니다.

```powershell
.\install\verify-search.ps1 --query "주문 전송 실패"
```

코드를 수정한 뒤 다시 검색했을 때 `STALE_KNOWLEDGE`가 나오면 같은 절차를 반복합니다.

```powershell
.\install\run.ps1 sync

# generated/review-queue.md와 변경된 원문을 실제 검토하고 문서를 수정

.\install\run.ps1 accept-review `
  --note "배송 실패 재시도 변경과 관련 문서를 현재 코드에 맞게 검토함"

.\install\run.ps1 sync
.\install\verify-search.ps1 --query "배송 실패 재시도"
```

즉, `accept-review`의 메모에는 `"최신화함"`처럼 모호한 문장보다 **어떤 코드·설정·문서를 대조했는지** 적는 것이 좋습니다.
